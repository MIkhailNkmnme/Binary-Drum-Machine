## Роли, модели и сложность

Пользователь явно разрешил эту схему и самостоятельное распределение задач по сложности. Выбирать конкретную модель из таблицы; не заменять её просто потому, что вышла более новая.

| Роль / задача | Модель | Рассуждение | Когда выбирать |
|---|---|---|---|
| Координатор | `gpt-6-astra` (Astra) | `high` | Разбиение работы, зависимости, решения и приёмка |
| Простая | `gpt-6-luna` (Luna) | `low` | Узкая понятная правка, сбор сведений, оформление, без сложной геометрии |
| Обычная реализация | `gpt-6.1-sol` (Sol) | `medium` | Локальная функция, интерфейс, типичная диагностика и её проверки |
| Сложная / сложная проверка | `gpt-6-astra` (Astra) | `high` | Архитектура, геометрия/XOR, неоднозначный дефект, взаимодействие нескольких модулей |

- Координатор оценивает сложность перед выдачей задания, записывает основание в карточке и может повысить категорию после новых фактов. Не расходовать сложную модель на механическую работу без причины.
- В карточке различать **назначенную** и **фактическую** модель/уровень. Если фактические настройки не видны, писать «не подтверждено», не угадывать.
- Документ не меняет модель текущего главного чата. Если он запущен с другими настройками, сообщить об этом; переключать только доступным поддержанным способом.
- В текущих инструментах внутренний субагент с полной историей наследует модель и уровень родителя. Для отдельной модели запускать его с коротким самостоятельным заданием без полной истории, если среда это поддерживает.
- Если модель недоступна, зафиксировать препятствие и назвать доступную замену и её причину. Не приписывать заменённому исполнителю исходную модель. Уровни выше `high` требуют отдельного решения пользователя.
- Эта схема относится к Codex/OpenAI. В другой системе сначала проверить доступные модели; названия не означают наличие там OpenAI-моделей.

## Постановка и исполнение

1. При старте проверить репозиторий, ветку, HEAD, рабочие изменения и актуальность origin/main. Не стирать и не включать в свой коммит чужие незавершённые правки.
2. Прочитать документы состояния. Старое сообщение или отметка в журнале — повод проверить задачу, а не доказательство, что она всё ещё актуальна.
3. Создать карточку с ID, целью, критериями готовности, этапами/весами, приоритетом и зависимостями. Не начинать соседние продуктовые задачи только из-за их упоминания в журнале.
4. Выдать исполнителю: ID, цель, файлы, ограничения, модель/уровень, входные данные, критерии проверки и ожидаемый короткий отчёт. Передавать нужные выдержки, а не весь разговор.
5. Для разовой независимой работы использовать внутренних субагентов. Отдельные постоянные чаты создавать только по явному запросу пользователя на создание таких чатов; эта инструкция сама новые чаты не создаёт. Сообщения в существующие чаты допустимы при пользовательском разрешении на их координацию; иначе использовать субагентов.
6. Координатор принимает результат: проверяет diff, необходимые проверки и критерии. «Исполнитель закончил» не равно «готово».
7. Обновить карточку, журнал, решения и продолжение; опубликовать законченный этап. Указать результат проверки публикации.

## Параллельность и расход

- Назначать владельца каждого набора файлов. Один и тот же файл параллельно не изменять; независимую работу изолировать веткой/worktree, когда это нужно. Не переключать общую ветку из-под другого исполнителя.
- Общие ЗАДАЧИ.md, ПРОДОЛЖИТЬ.md и РЕШЕНИЯ.md обновляет один координатор. Исполнители передают отчёт: что изменено, где, чем проверено, что осталось.
- Начинать с одного исполнителя; добавлять параллельных только для независимых частей. Не запускать нескольких агентов для одной механической задачи.
- Бюджет и лимит параллельности отмечать в карточке, если они заданы. Токены всех агентов суммируются; параллельная работа не означает экономию.
- Указывать измеренный расход только при наличии показаний. Если счётчик не доступен, писать «нет данных», не оценивать расход на глаз.

## Этапы и проценты

- Статусы: очередь; в работе; проверка; готово; заблокировано; отложено; требует сверки; отменено.
- Этапы: постановка → подготовка → реализация → проверка → публикация → завершено. Статус и этап — разные поля.
- Процент = округлённая сумма весов **проверенно завершённых** пунктов / сумма весов всех пунктов × 100. Одинаковые веса допустимы. Отметка [x] требует основания. Открытый пункт даёт 0 своего веса; при необходимости разбить его на части.
- 100% — все критерии и обязательные проверки выполнены, публикация подтверждена. Если публикация — последний пункт, выставлять его после подтверждения доставки предшествующего коммита; затем публиковать закрывающую запись. Собственный хеш этой записи не требуется.
- Для неизвестного старого объёма писать «не оценён», а не 0% или 90%. При блокировке сохранять достигнутый процент, указать препятствие и действие для снятия.
- Общий процент показывать только для заранее определённой цели с весами задач. Не называть долю одной задачи процентом готовности всего Zerkulis. Меняя объём/веса, записать причину пересчёта.

## GitHub и смена компьютера/аккаунта

- На GitHub видно последнее опубликованное состояние, а не живое состояние процессов. Автоматического фонового обновления эта документация не создаёт.
- Публиковать после значимого законченного этапа и перед передачей работы. Если пользователь явно сказал «потом гит», сохранить локально и пометить публикацию отложенной.
- Перед публикацией сверить свежий origin/main; сохранить чужие изменения. Не применять force push и не откатывать чужие коммиты. Публиковать только файлы своей задачи.
- Для правок только документации: проверить ссылки, соответствие статусов и расчёт процентов, diff и состав коммита. При изменении кода выполнить относящиеся к нему проверки по AGENTS.md. Успех статической проверки не выдавать за визуальную проверку.
- После публикации проверить удалённую ветку/содержимое. При ошибке оставить точное локальное состояние и следующий шаг; прямо сообщить, что GitHub не обновлён.
- В публичных файлах не размещать секреты, токены, пароли, выгрузки учётных данных и частные материалы. На закрытые материалы давать только безопасную ссылку и отметить необходимость доступа.
- На другом компьютере сначала сверить изменения, обновить копию проекта через Git и прочитать ПРОДОЛЖИТЬ.md. Одинаковая папка E: не гарантирует одинаковое содержимое.
- Смена GPT-аккаунта не переносит живых исполнителей и историю разговоров. Новый координатор восстанавливает работу из файлов и повторно проверяет доступные модели/инструменты.

## Сжатие контекста и передача

Перед /compact, завершением или переносом записать: цель; ID и статус; выполненные пункты и доказательства; оставшиеся шаги; решения; препятствия; изменённые файлы; репозиторий/ветку/коммит; что опубликовано и что осталось локально. Активного исполнителя не считать перенесённым: проверить результат либо явно передать незавершённую часть.

Реестр файлов не является планировщиком, не запускает агентов и не поддерживает работу при выключенном исполнителе. Если требуется фоновая автоматизация, это отдельная задача.
